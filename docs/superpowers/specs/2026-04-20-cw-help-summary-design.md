# `trail cw --help` 分组摘要设计

## 背景

当前 `trail cw --help` 与 `trail cw <group> --help` 基本只列出命令名，几乎不提供可指导下一步动作的有效信息。

现状问题：

1. `trail cw --help` 只能看到 `enter`、`portal`、`shop` 等分组名，看不出各自负责哪个阶段。
2. `trail cw shop --help`、`trail cw stage --help` 这类子组帮助也缺少一句用途说明，用户必须读源码或 README 才能理解。
3. 仓库里已经有更好的正例：`trail start`、`trail window launch`、`trail ocr read` 都通过 `help=` 或 docstring 暴露了关键语义；`cw` 这条场景链路还没补上同等级信息。

用户这次明确收窄了范围：

- 先只补 `cw` 顶层和各子组的用途摘要
- 不要求这次补叶子命令的参数帮助
- 帮助文本以“用途摘要”为主，不额外做流程引导版长文案

这里的“顶层”特指 `trail cw --help` 自身的总述文本；不是要求把所有叶子命令都扩成完整帮助页。

## 目标

1. 让 `trail cw --help` 能直接说明各分组的职责边界。
2. 让 `trail cw <group> --help` 至少包含一句可读的用途摘要。
3. 保持帮助文本简短，优先回答“这个分组是干什么的”。
4. 用自动化测试锁定这些摘要，避免后续再次退化成空帮助。

## 非目标

这次不做：

- 叶子命令参数帮助补全，例如 `trail cw start --help`、`trail cw portal select --help`
- 新增命令、调整 canonical command、变更默认输出协议
- 在 `--help` 中加入完整操作流程、长示例或恢复路径
- 重构 `cw` 命令注册方式

## 方案比较

### 方案 A：直接在 `cw.py` 上补 `Typer(help=...)`

做法：

- 给 `cw_app` 加顶层 `help=`
- 给各子组 `Typer` 加一句摘要式 `help=`
- 继续沿用现有 `cw_app.add_typer(...)` 组装方式

优点：

- 改动最小，和当前代码结构最贴合
- Typer 会同时把这类描述用于顶层分组列表和子组自己的 `--help`
- 容易补测试，不需要引入新抽象

缺点：

- 文案分散在 `cw.py` 里维护
- 后续若要统一抽文案表，还需要再整理一次

### 方案 B：抽一份集中式 `cw` 帮助文案表

做法：

- 先定义 `group -> help text` 映射
- 再用这份映射注册各个子组

优点：

- 文案集中，后续统一维护更方便

缺点：

- 这次收益有限，却引入一层额外抽象
- 对当前问题来说有些过度设计

### 方案 C：做成更强的命令元数据驱动

做法：

- 让帮助、README、文档未来都从同一份命令元数据生成

优点：

- 长期一致性最好

缺点：

- 明显超出这次“只补分组摘要”的范围
- 会把一个小修复膨胀成注册系统改造

## 结论

采用 **方案 A**。

理由：

- 这次问题很明确，就是 `cw` 分组帮助缺失。
- 用户已经明确要求“只补分组”“用途摘要优先”。
- 最小正确改动就是在现有 `Typer` 定义处把帮助文案补齐，再用测试锁住。

## 设计细节

### 顶层 `cw` 帮助

`trail cw --help` 需要新增一句顶层摘要，明确它是货币战争的固定流程命令集，而不是通用杂项入口。

文案方向：

- 一句话概括 `cw` 负责“货币战争场景固定流程”
- 在这句总述里顺带完成 `enter` / `start` 的最小语义辨识：`enter` 到首页，`start` 从首页进入投资环境页
- 不在顶层帮助里展开完整玩法说明
- 保持和 README 中“命令面概览”一致的术语

这里冻结一个边界：

- `enter` / `start` 的辨识通过 `cw_app` 自身的顶层摘要完成
- 本次**不**扩写 `trail cw enter --help` / `trail cw start --help` 的参数帮助
- 本次也**不**要求在 `trail cw --help` 的命令表里给 `enter` / `start` 单独补长描述

### 子组摘要

每个子组只保留一句用途摘要，重点是职责边界，而不是执行步骤。

文案约束：

1. 尽量使用“动词 + 场景对象”的短句。
2. 优先描述这个分组处理哪个阶段或资源。
3. 避免把多个阶段混在一句里，尤其不要把 `portal` 和 `invest`、`guide` 和 `stage` 混淆。
4. 保持现有术语一致，例如“首页”“投资环境页”“局内事件”“商店”“编队”。

### 易混边界

后续实现文案时，至少要冻结以下边界：

- `trail cw guide` 只表示**当前对局攻略的 apply/current**；不要写成“攻略列表”“攻略筛选”或“拉取攻略”，这些属于顶层 `trail guide ... cw`
- `portal` 只表示**投资环境页上的显式动作**，例如选卡、刷新、重开；不要写成“进入投资环境页”，因为进入该页是 `start`
- `stage` 只表示**阶段检测 / 等待**；不要写成“处理阶段”或“推进流程”
- `invest` 只表示**局内 invest 事件**；不要写成开局投资环境页
- `event` 不是所有事件的总称；`replenish`、`invest`、`encounter`、`fortune` 已各自有独立分组，`event` 只能概括剩余的通用/特殊事件处理

预期覆盖的分组包括：

- `guide`
- `portal`
- `stage`
- `slots`
- `shop`
- `crystals`
- `hand`
- `replenish`
- `invest`
- `encounter`
- `fortune`
- `boss-preview`
- `battle`
- `settle`
- `event`

### 实现方式

实现保持在 `trail/commands/cw.py` 内完成：

1. 给 `cw_app = typer.Typer(...)` 增加顶层 `help=`。
2. 给每个子组 `Typer(...)` 增加一句 `help=`。
3. 不新增 callback，不引入新的注册层。

选择 `Typer(help=...)` 而不是额外 callback/docstring 的原因：

- 对子组命令来说，这是最直接的绑定点。
- 同一份文案可以同时出现在父级分组列表和子组自己的帮助页里。
- 代码改动更少，也更不容易影响已有命令调用路径。

## 测试与验证

测试在 `tests/test_atomic_commands.py` 增补或收紧：

1. `test_cw_help_exposes_scene_command_groups`
   - 保留现有“命令名可见”断言
   - 单独断言 `cw_app` 自身的顶层摘要存在
   - 在同一个 `cw --help` 输出里，对每个子组都断言一个短锚点，确认命令表不再是空白分组列表
2. 新增子组页级别帮助测试
   - 至少覆盖 `trail cw portal --help` 与 `trail cw shop --help`
   - 断言子组自己的帮助页会显示该组摘要
3. 把高混淆边界列为必测锚点
   - `portal` 的锚点必须指向投资环境页动作，而不是“进入投资环境页”
   - `invest` 的锚点必须指向局内 invest 事件
   - `stage` 的锚点必须指向检测 / 等待
   - `guide` 的锚点必须指向当前对局攻略 apply/current，而不是攻略列表查询

断言策略以“关键短语存在”为主，不锁死 Typer 的空格、换行和表格排版，避免测试对格式微调过度脆弱。

进一步约束：

- 优先断言短锚点，不对整句长文案做原样匹配
- 如需对较长帮助段做匹配，先做空白归一化后再断言
- README / skill 同步不纳入这组 CLI help 合约测试；它们属于实现清单中的文档任务

## 文档同步

按仓库约束，这类用户可见输出变化还要同步更新文档：

1. `README.md`
   - 必须检查并在必要时同步以下位置中涉及 `cw` 分组职责的句子：`命令面概览`、`货币战争流程`、`Skill 边界`
   - 如果这些段落现有表述已经与新 help 摘要一致，则不额外扩写
2. `skills/trail-cw/SKILL.md`
   - 这是必查同步点，因为它直接定义了 `enter` / `start` / `portal` / `invest` 等边界
3. `skills/trail-cw-guide/SKILL.md` 与 `skills/trail-cw-replenish/SKILL.md`
   - 这两份要检查并在术语不一致时同步，因为它们分别直接触达 `guide` 与 `invest` 的易混边界
4. 其他 `skills/trail-cw-*` 文档
   - 做一致性检查即可；若没有直接描述分组职责边界，可以不修改

这里再冻结一个边界：

- 本次 skill 同步只覆盖“职责说明 / 边界说明 / 直接解释 `enter`、`start`、`portal`、`invest`、`guide`、`stage` 的句子”
- 不因为 help 摘要变化去重写 `标准流程`、验收清单、恢复规则或整局编排说明

## 风险与边界

主要风险不是功能回归，而是文案失真：

- 如果摘要写得过泛，帮助仍然无效
- 如果摘要写得过长，会让 `--help` 再次变成难扫读的大段文本
- 如果 `portal` / `invest`、`guide` / `stage` 等边界写错，会反而误导 Agent

因此这次设计把范围收紧到“短摘要 + 稳定术语 + 测试锁定”，不顺手扩成流程说明系统。

额外禁写模式：

- 不写“先……再……”这类流程顺序句
- 不写“攻略优先 / 环境优先 / 是否刷开局”这类策略说明
- 不写恢复路径、失败排障、跨命名空间职责
- 不写“处理所有事件”“自动推进整局”这类全包型表述
